# 决策记录（改之前先读）

> 这里记的是**「为什么」**，不是「是什么」。每条都对应一次真实问题或一次用户看画面后的判断。
> 很多写法第一眼看着别扭，其实是踩过坑才定下来的；想「顺手改漂亮」之前先翻这里。
> 与 Go 引擎决策编号的关系见 [MAPPING.md](MAPPING.md)；本文档的 D 编号是 **demo 自己的**。

## D1. 独立项目，不跟 Go 引擎同步

**现象**：Go 引擎（`D:/go/goengine`）还在按 S04→…→V3 的关键路径持续更新。

**决定**：demo 放在并列的 `D:/go/ashen-vale`，是 2026-11-09 对 Go 架构的一次**静态快照式移植**，不是 fork、不是同步副本。不改 Go 仓库一个字节。

**为什么**：两条线目标不同——Go 是「为 AI 做游戏而设计的 ARPG 引擎」，demo 是给朋友快速上手的浏览器玩具。硬同步会把 Go 的存档/联机/Android/无头出图全拖进来。

**⚠️ 别改回去**：Go 后续更新时按 [MAPPING.md](MAPPING.md) 找对应 TS 文件**搬机制**，不要整包复制代码，也不要让 demo 反过来影响 Go 主线。

## D2. 零美术依赖：程序化生成一张图集

**现象**：要发给几个朋友，不能要求他们先下载素材、配路径、装图集工具。

**决定**：所有贴图由 `engine/art.ts` 在浏览器里画出来，行式装箱打进**一张** canvas → 一个 `TextureSource`；`atlas.get(name)` 按名字查；帧间留 2px gutter；`scaleMode = nearest`；查不到降级白点不崩。`__ASHEN__.dumpAtlas()` 可导出 `atlas.png` + `atlas.json`，放进 `public/assets/` 即可替换（D19 起改为 `?externalAtlas` 显式启用）。

**为什么**：一张图集 = Pixi 能批处理；gutter 等价于 Go 版 `rectUV` 半像素内缩，防最近邻串色；按名字查 = 换皮不用改代码。

**⚠️ 别改回去**：别给每个部件单独 `Texture.from()`（丢失批处理），别在运行时往图集里新增贴图（Go 版 D39/D29 反复踩过：启动时一次性上传）。细节见 [ART.md](ART.md)。

## D3. 视觉只有 3 套视角 + 镜像，没有 8 方向帧

**现象**：输入是鼠标/摇杆的连续弧度，做 8 套方向贴图成本很高。

**决定**：`facing.ts` 的 `facingView()` 用 `|cos| > |sin|` 对角线分界，归成 `front / back / side`；朝左 = `side` 贴图 + `scale.x = -1`。

**为什么**：分界在对角线上，斜着走不会频繁左右翻；朝左若旋转 180°，帽子、法杖、脸的光源会一起翻过去。

**⚠️ 别改回去**：这是 Go 版 D51/D52 定下的唯一朝向判据，判定与渲染必须共用同一份。要真等距/8 向，得同时改「方向输入 / 朝向归并 / 点击反变换 / 遮挡」四件事，不是加几张图就行（Go 的 T11 任务书里也还没做）。

## D4. 走路相位跟「实际位移」，不跟时间、不读输入

**现象**：早期的按时间播帧会打滑；贴墙被挡住时角色还在原地踏步。

**决定**：`phase += moved / 26 * π`，`blend` 由 `moved / dt` 平滑得到；表现层只比较这一帧与上一帧的**位置**，不读 `InputState`。

**为什么**：走快走慢脚不打滑、被墙挡住脚会停、以后客户端只收位置快照不跑模拟也画得对。

**⚠️ 别改回去**：改成「按 dt 推进 phase」或「读输入向量」会立刻退化成滑行。表现状态（phase/blend/lastPos/渲染时钟）存在 `renderer.ts` 的视图里，**不写回 ECS**。

---

## D5. 固定步长 1/60 + 系统顺序由 `main.ts` 定死

**现象**：变步长会让「同种子同输入 = 同结果」失效；系统各自拼顺序容易把冷却推进放到攻击判定之前。

**决定**：`loop.ts` 累加器，`MaxSteps = 5`；链是 `applyInput → tickTimers → updateAI → updateProjectiles → updateRules → flush`。

**为什么**：冷却必须在攻击判定**之后**推进，否则同一帧能打两次；封顶防止「卡 → 补 → 更卡」死亡螺旋。

**⚠️ 别改回去**：新增系统插在 `updateProjectiles` 之后、`flush()` 之前；别在 `tickTimers` 前面。模拟用固定 dt，表现用真实帧 dt，两套不要混。

---

## D6. 模拟只发事件，表现只消费

**现象**：加飘字/震屏/音效时，很容易顺手在模拟层里改渲染状态。

**决定**：`World.emit()` → `Presentation.consume(world.drain())`，**全项目只有一处 `drain()`**。走路相位、特效、随机抖动、渲染时钟全在渲染层。

**为什么**：保证「有没有渲染」不影响游戏结果，也是以后接服务端权威 / 回放的前提。

**⚠️ 别改回去**：加一种表现只改 `game/present.ts` 的 `consume()` 分支，模拟层零改动。事件里只放标量和坐标，别放对象引用（要能序列化）。

## D7. `Side` 是独立画法，不是正面裁一半

**现象**：用户看画面后连续两次反馈——「侧面能看见两条正面一样的腿」「身体和脚侧面还是不太行，太大了」。

**决定**：`drawBody` 的 side 分支自成一套：躯干 10px 宽（正面 14px）、后背压暗、**两腿前后错开且后腿只露一小截**；侧脸带鼻尖。**不画手臂、不画靴子、不画斗篷**（斗篷整体去掉，见 D13）。朝左靠 `scale.x = -1` 镜像。

**为什么**：早期版本让侧视复用正面的并排腿、还画了同色前臂和靴子，视觉上又被撑回正面那么宽；而**默认鼠标方向恰好就是 `side`**，一进游戏就露馅。

**⚠️ 别改回去**：这是两轮实测画面后的结论。要动侧视，先放大图集帧对比 `heroFrontBody` vs `heroSideBody`（用 `__ASHEN__.dumpAtlas()` 或 CDP 放大），别凭代码想象。

---

## D8. 悬浮手脚：静态贴图里没有手臂、腿段、鞋

**现象**：Go 版 D43 试过两段 IK 四肢，用户判断「骨架不太行，还是之前的悬浮手脚好」。

**决定**：Body 贴图**只画躯干 + 裤腿**；手是 6×6 方形像素块，鞋是独立小贴图，两者运行时按相位/锚点摆放；手臂段和腿段根本不画。

**为什么**：躯干只有十几像素宽，两段锥形在这个尺度下像竹竿，比「手是两个块、脚是两只鞋」更不像人。

**⚠️ 别改回去**：别往身体贴图里加手臂或靴子（会复现 D7），也别加 IK。Go 的 `limbs.go` 那套 IK 代码是归档状态，没有调用方。

## D9. 手位用三档离散锚点，刻意「不平滑」

**现象**：用户要求「把像素手回退到 go 的以前的不平滑的版本」。

**决定**：`HAND_ANCHORS[front|back|side][0|1]` 三档固定锚点 + `handBob()` 走路摆动；**不做 360° 连续插值**，过对角线时手直接跳到另一组锚点。手贴图是硬边方块，不是带高光的圆。

**为什么**：这是 goengine **D52 之前**的实现（`0eed0e0` 的 `handAnchors[3][2]`）；D52（`15315df`）之后 Go 才换成 `core.HandOffset` 极坐标连续插值。用户明确要旧版观感。

**⚠️ 别改回去**：不要「顺手」补一个角度插值让它变平滑，那正是被回退掉的版本。

---

## D10. 鞋是独立贴图，可换装

**现象**：用户提醒「脚穿上鞋子可以换装，你知道吧」。

**决定**：`shoe<Mat>[Side]` 共 10 张（5 材质 × 2 视角），`Equip.shoes` 存材质，渲染层每帧用 `shoeSpriteName(mat, isSide)` 拼名字换 texture。玩家装备鞋材质，亡者按腐肉色出赤脚；早期 `B` 循环操作已由 D17 的背包装备位替代。

**为什么**：对应 Go 版 `art.ShoeSprite(equip, view == ViewSide)` → `sprShoe<Mat>[Side]`，以及 `spr<Rig>ShoeBare[Side]` 按肤色出赤脚。鞋不画进身体，才能换装。

**⚠️ 别改回去**：侧视鞋是**单独一张**（有朝右鞋头和靴筒），不能拿正视图凑合——这正是 Go 命名里 `Side` 后缀特殊的原因。加材质走 `SHOE_MATERIALS` + `SHOE_COLORS`，别在渲染层写 if/else。

## D11. 有意偏离 Go 的三处

| 主题 | Go | demo | 为什么 |
|---|---|---|---|
| 渲染对象 | 每帧重建绘制指令（`Frame`） | **复用 Sprite 视图池** | Pixi 靠批处理，每帧 `new Sprite` 会直接失效 |
| ECS 反查 | `[]int32`，**必须初始化 -1** | `Map<Entity, number>` | 从根上消掉「0 是合法下标」那个坑；组件是引用语义，也不存在「读副本忘写回」 |
| 相机 Zoom | 钉死为 1（跨架构确定性约束） | `CFG.camera.zoom = 2`，随便调 | 浏览器单机 demo 没有跨后端确定性要求 |

**⚠️ 别改回去**：这三条是**有意**的，不是没搬全。理由与影响见 [MAPPING.md](MAPPING.md)「有意偏离的地方」。

## D12. 两个影响「第一眼」的小决定

- **默认瞄准点偏右**：`main.ts` 里把 `input.pointer` 初始化到屏幕中心右侧，否则鼠标没进过画面时角色会一直朝左上角，而 `side` 又恰好是最容易出问题的视角。
- **满血不画头顶血条**：一屏几十只怪，每只顶一条红条会像戴帽子，画面很吵；挨打后才显示。

**⚠️ 别改回去**：都是看画面后调的，不是随手写的默认值。

## D13. 斗篷先整体去掉

**现象**：用户问「人物侧面贴图后面有个背包一样的是啥」。定位到 `heroSideCloak`：侧视斗篷被画成 `x=5..11, y=15..34` 的一块 6×19 实心深色矩形，加顶/底横条，轮廓太规整，看起来就是背后挂了个方形背包。

**决定**：用户「先去掉斗篷」——把 `Cloak` 部件从**贴图生成、`Parts` 结构、渲染合成、图层常量**里一起拿掉，三视角都不再画；`LAYER.CLOAK` 也删了。

**为什么**：斗篷不是这套角色的必需部件（头 + 躯干 + 裤腿 + 悬浮手脚 + 武器已经完整）；先做减法，比把矩形硬修成披风更省事、也更不容易再画出别扭的形状。

**⚠️ 别改回去**：不要只删渲染层而留着贴图生成（白占图集），也不要只留 `atlas.get('...Cloak')`（会每帧打缺图警告、降级成白块）。以后要加回斗篷，必须同时改 `art.ts` 生成、`renderer.ts` 的 `Parts`、`layers.ts` 常量，并把侧视画成上窄下宽的梯形布片，而不是矩形。

## D14. 侧视兜帽要盖满额头，不能只盖后脑

**现象**：用户「侧面头盔没覆盖完全（跟秃头一样），正面是覆盖完额头的」。`drawHead` 的 side 分支里，兜帽只画了 `x=9..18, y=2..12`（左半后脑），头发只画 `x=10..18, y=2..9`；而头的基础皮肤是 `x=10..22, y=3..17`，于是**头顶前部 `x=18..22` 一大片皮肤露着**，侧视看着像秃顶。正面兜帽是 `x=9..23, y=2..11` 整幅压到眉上，两者对不上。

**决定**：侧视兜帽改成整幅 `x=9..23, y=2..11`（和正面同宽同高），加帽顶亮边、额前帽檐转折、后脑垂布；短发同样铺满 `x=10..23` 并留额前发际。只把眼睛以下的右半张脸和鼻尖露出来——鼻尖后画，压在帽檐前形成侧脸轮廓。

**为什么**：「侧视」指的是**脸朝右**，不是「帽子只画一半」。头部装备的覆盖范围应当三视角一致，否则转向时像突然摘了帽子/剃了头。

**⚠️ 别改回去**：改 `drawHead` 的 side 分支时，先量头部基础矩形 `p.outline(10,3,12,14)` 的横向范围，确保帽/发覆盖到 `x≈22`；只盖 `x<=18` 的老写法就是这次的 bug。`zombie` 走的是 `hair` 分支，别只修 `hood` 而漏掉它。验证方式：CDP 放大 `heroFrontHead` / `heroSideHead` / `casterSideHead` / `zombieSideHead` 四帧对比。

## D15. 源码构建单文件，分发产物不能成为另一套源码

**现象**：仓库同时有 TypeScript 源码、上传的历史 HTML 和一个空的「直接可以玩的 .HTML」，直接往压缩产物加补丁会使共创者继续改旧版本。

**决定**：增强功能落入 `src/` 原生模块。`npm run build` 输出常规网页，`npm run export:standalone` 用 Vite singlefile 从同一入口更新「直接可以玩的 .HTML」。保留上传 HTML 作为参考。

**为什么**：双击游玩不能加载外部 ESM 分片；开发者也需要类型检查、模块边界和可复现构建。两种构建必须来自同一套规则。

**别改回去**：不要手工改 minified Pixi 变量或用 prototype 覆盖系统，再把它当作源码整合。提交前同时检查 typecheck、test、两种 build 和浏览器。

## D16. 墙与人物按脚底排序，局部遮挡只影响表现

**现象**：旧南墙整图位于实体之上，人物走到墙前仍会被盖住；人物腰带锚点又与碰撞位置错开。

**决定**：地面仍烘焙为一张图；墙改用共享图集里的 32×64 立体帧，放到 entityLayer，以墙脚 Y 排序；人形部件统一上移 12 局部像素，让脚底 / 影子与碰撞点重合。只让盖住玩家的局部墙体 / 树冠淡出。

**为什么**：深度参考点必须相同，改变透明度不应改变碰撞或 ECS。墙帧、道具图标、法术和火光仍在启动时一次性生成到同一个 TextureSource。

**别改回去**：不要恢复最高层的整张南墙，不要在 renderer 临时写 Facing 或位置。显示方向迟滞只存在视图中，移动相位仍只跟实际位移。

## D17. 背包命令驱动，暂停不能丢物品或继续挨打

**现象**：点击拆分、合成、换装如果直接写界面数组，会与规则或快捷栏产生两套状态；满包时先清理地面掉落会吞物。

**决定**：玩家新增 `inventory` Store（36 格中前 9 格共用为快捷栏、4 合成格、靴子位、手持堆栈）。UI 只发 `InventoryCommand`，main 统一应用；装备由命令同步，拾取先入包再删除，补给箱先在副本上试放。关包时返还手持堆栈，放不下就保留弹窗。菜单 / 手册 / 背包暂停整个模拟，命令仍可处理。

**为什么**：一个模型才有堆叠守恒。UI 不需要认识伤害、物品生成或装备减伤，纯模型可用无浏览器测试验证。

**别改回去**：不要把背包复制进 DOM 层；不要只暂停输入而继续 AI / 计时；不要在未放下鼠标堆栈时隐藏它。

## D18. 墙体判定统一、技能数据独立，模拟不用浏览器时钟

**现象**：旧半格采样会漏掉短对角墙角，投射物可能从贴身墙另一侧出生；只有法师施法检查视线，近战和爆炸仍能穿墙。

**决定**：Level 使用 supercover 网格视线；投射物枪口逐段推进，飞行分段扫掠地形，再查可破坏实体。近战、爆炸、新星、闪电每一跳都检查相同视线。五系特殊技冷却独立存 Player；雷暴场是可序列化的 field 组件，删除走 flush。新增字段使用数组而不是 Set。

**为什么**：切换法杖不能绕过冷却；墙体对所有攻击应当一致。特效只通过标量 ring / bolt 事件输出，渲染不影响技能结果。

**别改回去**：不要从模拟调用 performance.now / DOM / Pixi；不要让特效回调扣血；不要在遍历 Store 时删除实体。怪物分离仍是先计算、后写位置的两段式，距离场按地图 revision 失效。

## D19. 外部图集显式启用，旧图集缺帧整体回退

**现象**：默认探测不存在的 assets/atlas.json 造成 404；旧版外部图集不含新法杖、物品和立体墙帧时会出现白块。

**决定**：默认只用程序化图集；网址加 `?externalAtlas` 才加载外部图集，file 协议始终跳过。验证新帧清单，缺帧则整套回退。

**为什么**：零素材依赖与离线加载应当真的是零外部请求，单张图集约定也不应被部分贴图 fallback 打破。

**别改回去**：不要按道具逐个创建 TextureSource，不要恢复每次启动的无条件网络探测。更新外部美术前先导出本版本完整模板。
